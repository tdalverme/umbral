# Chat Streaming Contracts v1 (H4.3)

**Feature**: 011-conversational-ui | **Date**: 2026-08-10

Planning contract for the chat streaming surface. Machine-checkable files:
`contracts/agent/v3/*.json` (state/topology/reply/intent),
`contracts/chat/v1/streaming-events-v1.json` (SSE event types) and the
OpenAPI `contracts/openapi/v1/openapi.json` (additive chat + proposal
paths). Product events: 0 new types (R-16).

## 1. HTTP surface (OpenAPI additive, R-08)

| Method | Path | Request | Response | Errors (problem+json) |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/chat/sessions` | `{search_profile_id}` | 201 session | `product.search_profile.read` denied → 403; validation → 422 |
| GET | `/api/v1/chat/sessions?search_profile_id=` | — | 200 session list | 403 denied |
| GET | `/api/v1/chat/sessions/{session_id}` | — | 200 session | `chat.session_not_found` 404 |

`access_control.authorize(action, resource_owner_id=user_id)`:
`product.chat.session.create/read`, `product.chat.message.write`,
`product.chat.decision.write`; 0 cross access with manipulated ids.

## 2. SSE wire format (R-07)

`Content-Type: text/event-stream`. Envelope:

```
event: <type>
id: <sequence>
data: <json payload>
```

Events (defined in `contracts/chat/v1/streaming-events-v1.json`):

| event | data payload | Meaning |
| --- | --- | --- |
| `chat.run_started` | `{run_id, session_id}` | turn claimed, run created |
| `chat.reply_fragment` | `{run_id, delta}` | chunk of the assistant reply (deterministic word-boundary chunks, `AGENT_REPLY_CHUNK_WORDS`) |
| `chat.tool_activity` | `{run_id, tool, status}` | tool executed (status: success/failure), no payload |
| `chat.interrupt_waiting` | `{run_id, interrupt: {type: "proposal_decision", proposal_id, diff, impact, expires_at}}` | HITL waiting on a proposal decision |
| `chat.run_completed` | `{run_id, message_id}` | turn finished, assistant message persisted |
| `chat.run_failed` | `{run_id, error_code}` | turn failed with typed code |
| `chat.run_interrupted` | `{run_id}` | turn interrupted (resume expected) |

Sequencing: `id` is monotonic per stream. The client dedupes by
`(run_id, id)`; reconnect resumes via `POST /resume` with the same run
claim (0 parallel runs, 0 duplicated effects, R-13).

## 3. Decision payloads (R-04/R-05)

```
approve: {kind: "approve", idempotency_key}
reject:  {kind: "reject", reason?: string (<=200), idempotency_key}
edit:    {kind: "edit", change: {<profile field change, same keys as
         propose H4.2>}, idempotency_key}
```

- The decision resumes the SAME interrupted run (`Command(resume=...)`).
- Cross-check: the run's checkpoint `pending_action` must reference the
  proposal id of the decision → else `agent.decision_mismatch`.
- Approve → existing apply path (confirmation + idempotency key, H4.2).
- Reject → `rejected('user')` + `rejection_note` (R-05).
- Edit → derived proposal (original `rejected('edited')` +
  `superseded_by_proposal_id`), emits `search_profile.update_proposed.v1`,
  and the run interrupts again waiting on the derived proposal (R-05).

## 4. Intent taxonomy and tool policy (R-01/R-02)

`intent-schema-v3.json` declares:

| intent | allowed_tools | Behavior |
| --- | --- | --- |
| consulta | get_search_profile, find_matches, explain_match, search_urban_context | read-only answers, grounded refs |
| refinamiento | propose_search_profile_update | propose → HITL; never direct apply |
| comparacion | compare_listings | structured comparison, no generative winner |
| feedback | record_feedback | like/dislike + optional reasons |
| fuera_de_alcance | (none) | grounded refusal + structured redirect |

Tool calls generated by the model are validated against this policy before
execution; violations → typed error in `tool_results`, 0 execution, 0
effects (deterministic, abuse-suite-testable).

## 5. Clarification policy (R-03)

High-impact keys: `budget`, `zona`, `hard_filters`, `radio`. Trigger:
confidence < `AGENT_CLARIFICATION_MIN_CONFIDENCE` (0.6), missing but
needed, or contradiction with the current profile snapshot. Max rounds:
`AGENT_CLARIFICATION_MAX_ROUNDS` (2); exhausted → grounded refusal +
structured UI suggestion. Questions: deterministic per-key templates,
Spanish (CABA), no PII, no other-radar data.

## 6. Contextual entry (UM-H4-025, P1)

User message `context: {entity: "listing"|"comparison", id}` keeps the
session scope and bounds the evidence scope to that object; tools remain
session-scoped (membership validated), citations link back to the correct
detail/comparator view.

## 7. Web BFF mapping (R-12)

`/api/radar/chat/*` route handlers proxy 1:1 to the above paths;
`forwardStream` pipes SSE without buffering (Cookie + BFF token +
correlation preserved). 0 direct browser calls to the private API.
